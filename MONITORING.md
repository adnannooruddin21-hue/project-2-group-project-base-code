# Monitoring

## Dashboard design

Dashboard name: **`P2-Order-Inventory`** (region `eu-north-1`), defined in [`config/dashboard.json`](config/dashboard.json).

7 widgets, deliberately laid out with visual hierarchy:

```
+--------------------------------------------------------------+
| Header (title, instance ID, namespace, region)                |
+---------------+---------------+---------------+---------------+
| Traffic       | Errors        | Latency       | Saturation    |
| (Golden       | (Golden       | (Golden       | (Golden       |
|  Signal)      |  Signal)      |  Signal)      |  Signal)      |
+---------------+---------------+---------------+---------------+
| Orders & Revenue              | Stock Level per SKU            |
| (business detail)             | (business detail)              |
+--------------------------------+--------------------------------+
```

The four Golden Signals sit in the most prominent row (top, immediately visible without scrolling). Business-detail widgets sit below — useful, but secondary to "is the system healthy."

## Golden Signals — widget by widget

### Traffic
**Shows:** `orders_created` (summed across all SKUs) and `reservation_attempts`, as a rate per minute.
**Why this chart type:** line chart — traffic is inherently a rate-over-time signal, a line makes trend and spikes immediately visible.
**How to use during an incident:** a flat line near zero when you expect traffic means either nothing is reaching the app (check the security group, check DNS/IP) or nothing is being sent (check the traffic source) — rules out "the app is broken" as the first hypothesis.

### Errors
**Shows:** `order_errors` and `reservation_failures`, automatically broken out by `reason` (and `sku` for stock-related failures) via `SEARCH()`.
**Why this chart type:** multi-series line chart — seeing *which* reason is spiking (validation vs. rejected vs. downstream-unreachable) is more actionable than a single "error count" number, and was exactly what let Incident #2's investigation distinguish a dependency outage from ordinary bad input at a glance.
**How to use during an incident:** check which specific reason-line is elevated before touching any code — a spike isolated to `reservation_failures insufficient_stock SKU-004` is a business/inventory problem, not an application bug; a spike in `order_errors inventory_unreachable` (as in Incident #2) is a dependency problem.

### Latency
**Shows:** `order_latency` and `reservation_latency`, both average and p95.
**Why this chart type:** line chart, with p95 alongside average — an average alone hides tail latency; showing both together is what let Incident #3 detect a real-but-small (~2-3x baseline) latency increase during CPU saturation.
**How to use during an incident:** if p95 diverges sharply from average, a subset of requests are much slower than the rest (worth investigating what they have in common); if both rise together, it's a broad slowdown affecting all requests.

### Saturation
**Shows:** CPU user %, CPU system %, memory %, disk %, all 0-100 scale.
**Why this chart type:** line chart, not stacked — these are four independent percentages, not components that sum to a meaningful total, so stacking them would visually imply a false relationship.
**How to use during an incident:** this is the first widget to check when latency or errors are elevated with no obvious application-level cause — Incident #1 showed a pure-CPU event with zero corresponding log output, meaning **only this widget** would have surfaced it.

## Business-detail widgets

### Orders & Revenue
**Shows:** `orders_created` (left axis, count) and `order_value` (right axis, USD) together.
**Why this chart type:** dual-axis line chart — ties a technical count metric to the actual dollar impact in one view, which is the point of a *business* metric.

### Stock Level per SKU
**Shows:** `stock_level`, one line per SKU (auto-generated by `SEARCH()`).
**Why this chart type:** line chart — watching a line trend toward zero is a directly actionable "about to sell out" signal. Note: SKU-004 never appears on this chart (verified, not a bug) because it's seeded at 0 stock and never has a *successful* reservation to report a level from — its state is visible in the Errors widget instead (`reservation_failures insufficient_stock SKU-004`).

## Technical design note: SEARCH() over hardcoded dimensions

While building this dashboard, querying real CloudWatch data revealed two things that would have broken hardcoded metric references:
1. The CloudWatch Agent silently adds a `metric_type` dimension to every StatsD metric.
2. `reservation_failures` has an *inconsistent* dimension set — the `insufficient_stock` reason carries an extra `sku` dimension the other reasons don't.

Every widget therefore uses `SEARCH('Namespace="P2OrderInventory" MetricName="..."', 'Statistic', Period)` rather than fixed `[Namespace, MetricName, Dim, Value, ...]` arrays, so new dimension combinations (a new SKU, a new failure reason) show up automatically without editing the dashboard. This was verified against real data (`get-metric-data`) before being committed, not assumed to work.

## How to use the dashboard during an incident (general procedure)

1. **Look at the top row first** (Golden Signals) — which one is abnormal tells you the failure *class* before you open a single log line: Saturation-only → infrastructure; Errors-only → application/dependency; both → possibly related (see Incident #3).
2. **Check the Errors widget's reason breakdown** — narrows "something failed" to a specific cause.
3. **Cross-reference the time window against CloudWatch Logs Insights** using the correlation ID pattern from [INSTRUMENTATION.md](INSTRUMENTATION.md) to see the exact requests affected.
4. **Don't guess — this is what the three documented incidents in [INCIDENTS.md](INCIDENTS.md) demonstrate**: each root cause was confirmed with dashboard/log/alarm evidence, not assumed from symptoms alone.
