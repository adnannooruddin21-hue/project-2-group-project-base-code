# Incidents

Failure scenarios intentionally injected during Project 2 testing, investigated using the CloudWatch dashboard, alarms, and structured logs built in this project — not guessed.

---

## Incident #1 — High CPU (injected)

**Date/time:** 2026-08-13, 08:21-08:29 UTC (stress load ~08:21-08:25, alarm ALARM 08:25-08:29 UTC)

**Type:** Intentional failure injection (controlled test, not a real production incident)

### Symptoms
- CloudWatch alarm `p2-order-inventory-cpu-critical` transitioned `OK → ALARM` at 08:25 UTC.
- Dashboard Saturation widget showed CPU user/system utilization at 100% (both stress-ng workers pegged both vCPUs on the t3.micro instance).

### Impact
Contained to the test itself — no real users, no data loss (app is stateless/in-memory by design). In a production system, sustained 100% CPU would be expected to degrade request latency and potentially exhaust the t3.micro's CPU credit balance (a "burstable" instance type), leading to enforced throttling.

### Detection
Automated: the `cpu-critical` CloudWatch alarm (>80% for 2 of 3 one-minute periods) fired and sent an SNS email notification, which was received and confirmed by the operator. Detection was alarm-driven, not manual observation.

### Investigation
1. Confirmed the alarm's own reason string showed real breaching datapoints: `100.0 (08:21:00)`, `100.0 (08:22:00)` — both far above the 80% threshold and the ~0.3-0.6% observed baseline.
2. Checked `aws cloudwatch describe-alarm-history` for `p2-order-inventory-cpu-critical` — confirmed a clean `OK → ALARM` transition at 08:25:02 UTC and `ALARM → OK` at 08:29:02 UTC, each with a successfully-executed SNS action.
3. Attempted to correlate against `order_latency` (p95) during the same window to answer "did CPU contention also slow down request handling?" — **inconclusive**. The background traffic generator (Step 3) had already finished (~2 minutes of traffic) before the CPU stress load actually reached its sustained-high state, so there wasn't overlapping request traffic during the peak CPU window to measure latency against. This is a test-design gap, not a finding — see Lessons Learned.

### Metrics observed
- `cpu_usage_user` + `cpu_usage_system` (namespace `P2OrderInventory`): baseline ~0.3-0.6%, peaked at 100% during the injected load.
- `order_latency` p95: no usable overlapping datapoints during the peak window (see Investigation above).

### Logs observed
No application-level ERROR/WARN logs were generated by this scenario — this failure is purely infrastructure-level (CPU saturation), not something the application code itself detects or logs. This is itself a useful observation: **application logs alone would not have surfaced this incident** — only the CloudWatch Agent's OS-level metrics did. Confirms the value of collecting resource metrics (CPU/mem/disk) alongside application logs, not just one or the other.

### Root cause
Deliberately injected via `stress-ng --cpu 2 --timeout 240s`, run directly on the EC2 instance via SSM Session Manager. Not a real defect.

### Immediate fix
None needed — `stress-ng` has a built-in timeout and exited on its own after 240 seconds. CPU returned to baseline (~0.5-0.6%) without any manual intervention, and the alarm self-resolved to `OK`.

### Long-term fix (if this were a real recurring issue)
- Consider CloudWatch alarm-triggered auto-scaling or an EC2 Auto Scaling group if this workload's traffic pattern genuinely produces sustained high CPU (not applicable to this toy project's traffic volume, but the standard real-world answer).
- Since `t3.micro` is a burstable instance type with a finite CPU credit balance, a **CPUCreditBalance** alarm would give earlier warning than waiting for utilization itself to cross 80% — flagged as a documentation note rather than implemented here, to keep the alarm set focused (see Alerting rubric: avoid vanity alarms).

### Lessons learned
1. **Test design gap**: to properly correlate CPU saturation with latency in a future test, traffic generation needs to run *for the full duration of* the CPU stress, not just beforehand. Scenario 3 (complex/multi-factor) will run both simultaneously to close this gap.
2. Infrastructure-level failures (CPU/memory/disk) don't show up in application logs at all — this is exactly why the assignment requires both log-based *and* resource-based monitoring, not just one.
3. The alarm's own `StateReason` field is a genuinely useful piece of evidence on its own — it includes the actual breaching datapoints inline, no separate metric query needed to prove what triggered it.
